Base de Conocimiento

Preguntas Frecuentes
(FAQ) Oracle SQL

Las respuestas a todas esas dudas existenciales sobre rendimiento, índices, seguridad y diseño que surgen cuando estás aprendiendo a dominar la base de datos.

Índices y Rendimiento

La magia detrás de las consultas rápidas.

1. ¿Por qué no le ponemos índices a TODAS las columnas y listo?

Porque la velocidad en lectura tiene un precio en escritura. Cada vez que haces un INSERT, UPDATE o DELETE, Oracle no solo debe modificar la tabla, sino también reorganizar todos los índices asociados. Si tienes 10 índices en una tabla, un simple INSERT es 11 veces más trabajo para el motor. ¡Usa índices solo en las columnas por las que realmente buscas información!

2. ¿Un índice SIEMPRE mejora el rendimiento?

No. Imagina que tienes un libro de 100 páginas y quieres buscar una palabra que aparece en 90 de esas páginas. Es más rápido simplemente leer el libro completo que estar yendo al índice alfabético, volver a la página, volver al índice... Si tu consulta va a devolver un gran porcentaje de las filas de la tabla (baja selectividad), Oracle decidirá ignorar el índice y hacer un FULL TABLE SCAN porque matemáticamente es más rápido.

3. ¿Qué tipo de columnas sí conviene indexar?
  • Columnas que se usan constantemente en cláusulas WHERE (ej: rut, correo, fecha).
  • Columnas que se usan para unir tablas en un JOIN (Llaves Foráneas).
  • Columnas usadas frecuentemente en ORDER BY.
  • Columnas con alta selectividad (es decir, tienen muchos valores distintos, de modo que buscar un valor específico devuelve muy poquitas filas).
4. ¿Qué son los índices compuestos?

Son índices creados sobre dos o más columnas a la vez (ej: CREATE INDEX idx_nombre_apellido ON clientes(nombre, apellido);). Son súper útiles cuando tu aplicación casi siempre filtra usando ambas columnas al mismo tiempo. Ojo: el orden importa. Si tu índice es (A, B) y solo filtras por B, Oracle probablemente no pueda usar el índice eficientemente.

Explain Plan y Pruebas

Cómo saber qué está pensando la base de datos.

5. ¿Qué es el EXPLAIN PLAN?

Es como pedirle el itinerario de viaje al GPS de Oracle. Antes de ejecutar una consulta, Oracle analiza múltiples caminos posibles y elige el "más barato". El EXPLAIN PLAN te dibuja en pantalla esa decisión, mostrándote paso a paso las operaciones que hará, los índices que usará y el Costo matemático estimado.

6. Hice un índice pero el EXPLAIN PLAN sigue mostrando "FULL TABLE SCAN". ¿Por qué?

Oracle evalúa los costos con IA matemática (el Optimizador). Si tu tabla tiene muy pocas filas (ej. 10 filas), leer la tabla entera es literalmente más rápido que ir a leer el índice y luego ir a la tabla. El índice empezará a brillar y a ser usado por Oracle cuando la tabla crezca a cientos o miles de registros.

7. ¿Por qué a veces una consulta rápida no significa que el diseño esté bien?

Porque las bases de datos usan memoria caché (RAM). Si ejecutas una consulta lenta, Oracle guarda el resultado en la RAM. Si la ejecutas de nuevo, será instantánea, no porque el índice sea bueno, sino porque lo leyó de la memoria. Por eso es vital mirar el Cost en el Explain Plan, no solo el reloj de tiempo.

Diseño e Integridad

Primary Keys, Foreign Keys, Identity y Secuencias.

8. ¿La PRIMARY KEY es lo mismo que un Índice?

No conceptualmente, pero sí en la práctica. La Primary Key es una regla de negocio (Restricción) que dice "No puedes repetir esto y no puede ser nulo". Para poder hacer cumplir esta regla rápidamente, Oracle crea automáticamente un Índice Único por detrás. O sea, toda PK viene con un índice gratis.

9. ¿La FOREIGN KEY crea un índice automáticamente?

¡NO! Y este es uno de los mayores errores de principiantes. Las Foráneas no crean índices solos. Si haces un `DELETE` en la tabla padre (ej. borrar una categoría), Oracle debe revisar TODA la tabla hija (ej. productos) para asegurarse de que ningún producto esté usando esa categoría. Si la FK no tiene índice, Oracle hará un Full Table Scan, y si hay millones de productos, borrar una categoría tomará minutos. ¡Siempre indexa tus Foreign Keys!

10. Diferencia entre IDENTITY y SEQUENCE

Ambos sirven para autoincrementar números (como el `AUTO_INCREMENT` de MySQL).

IDENTITY (disponible desde Oracle 12c) se asocia directamente a la columna al crear la tabla. Es más fácil y limpio.
SEQUENCE es un objeto separado de la tabla. Debes crearlo aparte y llamarlo con seq.NEXTVAL. Aunque es más "antiguo", se sigue usando mucho porque da mayor flexibilidad (una misma secuencia puede alimentar IDs a varias tablas distintas a la vez).

Seguridad y Privilegios

Controlando quién puede hacer qué.

11. Privilegios de Sistema vs. Privilegios de Objeto

De Sistema: Permisos para afectar la base de datos en general. Ejemplo: CREATE SESSION (poder conectarse) o CREATE TABLE (poder fabricar tablas propias).
De Objeto: Permisos para tocar cosas específicas que ya existen. Ejemplo: SELECT ON ventas.clientes (poder leer la tabla clientes del usuario 'ventas').

12. ¿Por qué usar ROLES en vez de asignar permisos directos?

Por pura sanidad mental. En una empresa real tienes 500 empleados de ventas. Si les das permisos uno por uno y luego deciden que Ventas ya no puede hacer DELETE, tendrías que ejecutar 500 veces REVOKE DELETE.... Si usas un Rol (una "mochila" con permisos), simplemente le quitas el permiso a la mochila una sola vez, y los 500 usuarios pierden el permiso instantáneamente.

El Mundo Laboral

Aplicando todo esto en la industria.

13. ¿Qué relación tiene todo esto con el trabajo real de un programador?

Muchísima. Cuando programes un backend (Java, Node, Python) y tu API empiece a responder lento con el paso de los meses, no va a ser culpa de tu código, sino de la base de datos que está haciendo Full Table Scans. Saber leer un Explain Plan y colocar el índice correcto es una habilidad de Senior que diferencia a los programadores junior que "reinician el servidor a ver si se arregla".

14. ¿Qué es mejor: crear un índice o reescribir la consulta SQL?

Siempre intenta mejorar la consulta primero. A veces la consulta está trayendo columnas innecesarias o usando lógicas súper rebuscadas. Si la consulta ya está limpia y estructurada, y aún así es lenta en tablas grandes, entonces entra a jugar el índice. Nunca uses índices para "parchar" malas consultas.

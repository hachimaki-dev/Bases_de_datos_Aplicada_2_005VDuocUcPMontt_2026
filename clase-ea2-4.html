El Problema: El "Full Table Scan"

Imagina que quieres buscar el apellido 'Pérez' en un libro telefónico que NO está ordenado alfabéticamente. ¿Qué tendrías que hacer? Tendrías que leer la página 1, luego la 2, luego la 3... hasta encontrar a Pérez, o hasta llegar al final del libro para asegurarte de que no hay más "Pérez".

A esto en bases de datos se le llama Full Table Scan (Escaneo Completo de Tabla). Cuando haces SELECT * FROM clientes WHERE apellido = 'Pérez';, Oracle revisará todas las filas si no sabe dónde está Pérez.

La Solución: El Índice

Un Índice en Oracle funciona exactamente igual que el índice alfabético al final de un libro. Es una estructura separada de la tabla que dice: "Pérez está en la fila 15 y en la fila 94". Así, Oracle va directo a esa fila sin leer el resto.

¿Cómo se usan los Índices?

A nivel práctico, el tipo de índice más común es el B-tree (Árbol B). Es el estándar por defecto. No necesitas especificar el tipo, Oracle lo crea por ti.

Casos Ideales para Índices

  • Columnas que usas mucho en condiciones WHERE (ej. RUT, Apellidos, Correos).
  • Columnas usadas para unir tablas en un JOIN (ej. las Claves Foráneas).
  • Columnas con alta selectividad (donde los valores casi no se repiten).
-- 1. Consulta lenta (Full Table Scan)
SELECT * FROM clientes WHERE apellido = 'Pérez';
SELECT * FROM pedidos WHERE id_cliente = 10;

-- 2. Creamos los Índices para acelerar esas búsquedas
-- Sintaxis: CREATE INDEX nombre_indice ON tabla(columna);
CREATE INDEX idx_clientes_apellido ON clientes(apellido);
CREATE INDEX idx_pedidos_id_cliente ON pedidos(id_cliente);

-- 3. Si ejecutamos las mismas consultas AHORA, 
-- Oracle usará automáticamente el índice (Index Range Scan)
SELECT * FROM clientes WHERE apellido = 'Pérez';

El Costo de los Índices

¿Por qué no indexar todas las columnas y ya? Porque los índices ocupan espacio en disco y, lo más importante, hacen más lentos los INSERT, UPDATE y DELETE. Cada vez que insertas un cliente nuevo, Oracle tiene que insertar el dato en la tabla y además actualizar el índice. ¡Usa índices solo donde haya muchas búsquedas!

Mantenimiento y Demostración

Eliminando Índices

Un error muy común en principiantes es intentar borrar un índice usando DELETE. Recuerda: `DELETE` es para borrar filas (DML). El índice es un objeto de la base de datos (como una tabla), por lo que se elimina con DROP.

DROP INDEX idx_clientes_apellido;

Comprobando la magia: El GPS de Oracle

¿Cómo estamos seguros de que Oracle está usando el atajo y no leyendo todo el libro? Existe una herramienta interna llamada EXPLAIN PLAN. Básicamente, es pedirle a Oracle que nos dibuje su ruta antes de ejecutar el viaje.

A continuación, te mostramos un resumen simplificado de lo que Oracle responde cuando le preguntamos su ruta. Nota la diferencia entre tomar el camino largo (Full Scan) y el atajo (Index Scan).

SIN ÍNDICE (El camino largo)
| Operation | Name | |-----------------------------|----------| | TABLE ACCESS FULL | CLIENTES |
CON ÍNDICE (El atajo)
| Operation | Name | |-----------------------------|-----------------------| | TABLE ACCESS BY INDEX ROWID| CLIENTES | | INDEX RANGE SCAN | IDX_CLIENTES_APELLIDO |

Resumen de Índices 🚀

Velocidad Extrema

Los índices evitan el "Full Table Scan", permitiendo que Oracle salte directamente a la fila que buscas, igual que buscar en el índice de un libro.

El Balance

No todo se indexa. Aceleran el SELECT, pero ralentizan el INSERT, UPDATE y DELETE porque requieren mantenimiento constante por parte del motor.

Adaptando el script a tus tablas

Si quieres usar este poder divino para llenar las tablas que tú mismo creaste en el taller (en vez de usar las de clientes/pedidos), debes cambiar los siguientes valores en el código:

  • Reemplaza INSERT INTO clientes por el nombre de tu tabla (ej: INSERT INTO videojuegos).
  • Cambia los nombres de las columnas (id_cliente, nombre, apellido, ciudad) por las tuyas.
  • Ajusta los tipos de datos que se generan en el SELECT debajo: Usa CHR(...) para generar letras aleatorias si tu columna es de texto, o DBMS_RANDOM.VALUE para generar números si tu columna es numérica.
stress_test_db.sql 
-- ============================================================
-- PASO 1: Inserción masiva recursiva con CONNECT BY
-- Genera ~1 millón de clientes, productos y pedidos
-- Usa secuencias y SELECT recursivo para máximo rendimiento
-- ============================================================

-- 1A) Crear secuencias para IDs únicos
CREATE SEQUENCE seq_cliente START WITH 100 INCREMENT BY 1 NOCACHE;
CREATE SEQUENCE seq_producto START WITH 1   INCREMENT BY 1 NOCACHE;
CREATE SEQUENCE seq_pedido  START WITH 1   INCREMENT BY 1 NOCACHE;

-- 1B) Insertar 1.000.000 de clientes en un solo INSERT
--     CONNECT BY LEVEL genera una fila por cada nivel (1..N)
--     MOD y CHR dan nombres/ciudades variados sin PL/SQL
INSERT INTO clientes (id_cliente, nombre, apellido, ciudad)
SELECT
    seq_cliente.NEXTVAL,
    CHR(65 + MOD(LEVEL,26)) || TO_CHAR(LEVEL)             AS nombre,
    CHR(65 + MOD(LEVEL+5,26)) || TO_CHAR(LEVEL*2)          AS apellido,
    CASE MOD(LEVEL,5)
        WHEN 0 THEN 'Santiago'
        WHEN 1 THEN 'Valparaíso'
        WHEN 2 THEN 'Puerto Montt'
        WHEN 3 THEN 'Concepción'
        ELSE       'Temuco'
    END                                                       AS ciudad
FROM DUAL
CONNECT BY LEVEL <= 1000000;

COMMIT;

-- 1C) Insertar 500.000 productos
INSERT INTO productos (id_producto, nombre, categoria, precio)
SELECT
    seq_producto.NEXTVAL,
    'Producto_' || LEVEL                                   AS nombre,
    CASE MOD(LEVEL,4)
        WHEN 0 THEN 'Electrónica'
        WHEN 1 THEN 'Ropa'
        WHEN 2 THEN 'Hogar'
        ELSE       'Alimentos'
    END                                                       AS categoria,
    ROUND(DBMS_RANDOM.VALUE(100,99999),2)                  AS precio
FROM DUAL
CONNECT BY LEVEL <= 500000;

COMMIT;

-- 1D) Insertar 2.000.000 de pedidos (apunta a clientes existentes)
INSERT INTO pedidos (id_pedido, id_cliente, fecha, total)
SELECT
    seq_pedido.NEXTVAL,
    -- id_cliente aleatorio entre los insertados (100 .. 100+999999)
    TRUNC(DBMS_RANDOM.VALUE(100, 1000099))                AS id_cliente,
    SYSDATE - TRUNC(DBMS_RANDOM.VALUE(0,1825))            AS fecha,
    ROUND(DBMS_RANDOM.VALUE(1000,5000000),2)              AS total
FROM DUAL
CONNECT BY LEVEL <= 2000000;

COMMIT;

Diseccionando el EXPLAIN PLAN

EXPLAIN PLAN no es magia. Es un comando real de Oracle que simula una consulta y te devuelve una tabla detallando los pasos exactos que el motor de la base de datos dará para encontrar tus datos.

¿Cómo se usa en la vida real?

Para obtener este plan, debes usar dos comandos. Primero, le dices a Oracle "Explícame el plan para esta consulta". Segundo, consultas la tabla especial donde Oracle guardó la respuesta.

-- 1. Pide la explicación (pon EXPLAIN PLAN FOR antes de tu SELECT)
EXPLAIN PLAN FOR
SELECT * FROM clientes WHERE apellido = 'Pérez';

-- 2. Lee la respuesta generada
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

¿Qué significan las columnas?

El resultado real tiene varias columnas, pero las tres más importantes para un desarrollador son:

  • Operation (Operación): Es la acción técnica. Si ves TABLE ACCESS FULL, Oracle está sudando la gota gorda leyendo toda la tabla. Si ves INDEX RANGE SCAN, Oracle está usando tu índice felizmente.
  • Name (Nombre): Te dice qué objeto específico está tocando en ese paso. Puede ser el nombre de la tabla (CLIENTES) o el nombre de tu índice (IDX_CLIENTES_APELLIDO).
  • Cost (Costo): Es un número matemático interno. Mientras más bajo, mejor. Es una estimación de cuánto esfuerzo de CPU y disco gastará Oracle. ¡Con índices verás que el costo se desploma!
